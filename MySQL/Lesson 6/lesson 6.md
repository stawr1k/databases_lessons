# Лекция 6: Индексы, оптимизация запросов (EXPLAIN) и современные возможности (JSON)

## 1. Введение: Почему базы данных начинают тормозить?

На этапе разработки, когда в таблицах хранится всего пара сотен строк, абсолютно любой SQL-запрос выполняется за десятые доли миллисекунды. Однако в продакшене, когда объем таблицы вырастает до сотен тысяч или миллионов строк, неоптимизированные запросы начинают «вешать» сервер.

Главная причина падения производительности — **Full Table Scan (Полное сканирование таблицы)**. Если у СУБД нет подсказок, как найти запись, ей приходится последовательно считывать с диска каждый байт каждой строки таблицы от первой до последней, что требует огромных затрат процессора и ввода-вывода (I/O).

Решением этой проблемы являются **индексы**.

## 2. Архитектура индексов в MySQL (B+ Tree)

**Индекс** в реляционной базе данных аналогичен алфавитному предметному указателю в конце толстой энциклопедии. Вместо того чтобы перечитывать 1000 страниц в поисках слова, вы открываете указатель, находите термин за 2 секунды и сразу переходите на нужную страницу.

В движке InnoDB все стандартные индексы строятся на базе самобалансирующихся сбалансированных деревьев — **B+ Деревьев (B+ Tree)**:

```
                      [  50  |  100  ]              <-- Корень дерева (Root)
                     /       |        \
                    /        |         \
           [ 10 | 30 ]  [ 60 | 80 ]  [ 120 | 150 ]   <-- Промежуточные узлы
            /   |   \    /   |   \    /    |    \
          Leaf Nodes (Листья дерева со ссылками на строки на диске)
```

Сложность поиска по B+ Дереву составляет **$O(\log N)$**: даже в таблице на 10 000 000 записей СУБД найдет нужную строку всего за 3–4 операции чтения узлов!

### Виды индексов в InnoDB:

1. **Кластерный индекс (Clustered Index):**  
   Формируется автоматически вокруг первичного ключа (`PRIMARY KEY`). Сама таблица физически упорядочена на диске по первичному ключу. В листьях кластерного индекса лежат **полные данные всей строки**.
2. **Вторичный индекс (Secondary Index):**  
   Пользовательские индексы по отдельным столбцам (`email`, `status`, `created_at`). В листьях вторичного индекса хранится значение индексируемого поля и соответствующий ему `PRIMARY KEY`.
3. **Покрывающий индекс (Covering Index):**  
   Идеальная ситуация, когда индекс содержит **все поля**, запрашиваемые в `SELECT`. СУБД отдает ответ напрямую из оперативной памяти индекса, даже не обращаясь к физической таблице на диске (`Extra: Using index`).

### Создание и удаление индексов

```sql
-- Обычный вторичный индекс по одной колонке
CREATE INDEX idx_users_email ON users(email);

-- Составной (композитный) индекс по нескольким колонкам
CREATE INDEX idx_orders_user_status ON orders(user_id, status);

-- Просмотр всех индексов таблицы
SHOW INDEX FROM orders;

-- Удаление индекса
DROP INDEX idx_users_email ON users;
```

### Правило крайнего левого префикса (Leftmost Prefix Rule)

Для составного индекса по колонкам `(A, B, C)` индекс может быть использован оптимизатором **только слева направо**:
* `WHERE A = 1` — ✅ Индекс используется (колонка A)
* `WHERE A = 1 AND B = 2` — ✅ Индекс используется (колонки A и B)
* `WHERE A = 1 AND B = 2 AND C = 3` — ✅ Индекс используется полностью
* `WHERE B = 2 AND C = 3` — ❌ Индекс **НЕ** используется (пропущен префикс A)
* `WHERE C = 3` — ❌ Индекс **НЕ** используется

## 3. Анализ плана выполнения запросов: EXPLAIN и EXPLAIN ANALYZE

Перед тем как оптимизировать медленный запрос, необходимо понять, какой план его выполнения построил оптимизатор MySQL. Для этого перед запросом добавляется ключевое слово **`EXPLAIN`**:

```sql
EXPLAIN SELECT * FROM users WHERE email = 'alex@example.com';
```

### Ключевые поля вывода EXPLAIN:

| Поле | Значение | Описание |
| :--- | :--- | :--- |
| **`type`** | **Критически важный маркер эффективности доступа!** |
| | `const` / `eq_ref` | **Идеально.** Чтение ровно одной строки по уникальному/первичному ключу. |
| | `ref` | **Отлично.** Поиск по обычному (неуникальному) индексу. |
| | `range` | **Хорошо.** Сканирование диапазона по индексу (`BETWEEN`, `>`, `<`). |
| | `index` | **Посредственно.** Полное сканирование дерева индекса. |
| | `ALL` | **Худший сценарий.** Полное сканирование всей таблицы (**Full Table Scan**). |
| **`possible_keys`** | Имена индексов, которые СУБД гипотетически могла бы применить. |
| **`key`** | Реальный индекс, выбранный оптимизатором. Если `NULL` — индекс не использован. |
| **`rows`** | Примерное число строк, которые серверу придется просмотреть. |
| **`Extra`** | Дополнительная информация. `Using filesort` или `Using temporary` означают тяжелые операции на диске/памяти. |

### EXPLAIN ANALYZE в MySQL 8.x

Начиная с MySQL 8.0.18, появилась революционная команда **`EXPLAIN ANALYZE`**. В отличие от обычного `EXPLAIN`, она реально исполняет запрос и замеряет точное фактическое время выполнения каждого шага в миллисекундах:

```sql
EXPLAIN ANALYZE SELECT * FROM orders WHERE total_amount > 10000;
```

## 4. Главные антипаттерны производительности SQL

1. **Применение функций к индексированным колонкам в WHERE:**
   ```sql
   -- ❌ ПЛОХО: Индекс по created_at полностью отключается!
   SELECT * FROM orders WHERE YEAR(created_at) = 2026;
   
   -- ✅ ХОРОШО: Индекс по диапазону прекрасно работает:
   SELECT * FROM orders WHERE created_at >= '2026-01-01' AND created_at < '2027-01-01';
   ```
2. **Поиск по шаблону с процентом в начале строки:**
   ```sql
   -- ❌ ПЛОХО: B-Tree не знает первой буквы, будет Full Table Scan:
   SELECT * FROM products WHERE title LIKE '%ноутбук';
   
   -- ✅ ХОРОШО: Индекс работает по префиксу:
   SELECT * FROM products WHERE title LIKE 'Ноутбук%';
   ```
3. **Неявное приведение типов (Implicit Casting):**  
   Если колонка `phone` объявлена как `VARCHAR(20)`, а вы передаете число `WHERE phone = 79991234567`, MySQL будет вынужден выполнить функцию приведения для каждой строки таблицы, проигнорировав индекс. Всегда передавайте строку: `WHERE phone = '79991234567'`.

## 5. Современные возможности: Нативный тип JSON в MySQL 8.x

Часто в реляционных проектах возникает необходимость хранить полуструктурированные данные с гибким набором свойств (динамические атрибуты товаров: цвет, вес, диагональ, память; настройки пользователя; полезную нагрузку вебхуков).

В MySQL 8.x встроен мощный нативный тип данных **`JSON`** с автоматической валидацией синтаксиса и бинарной оптимизацией хранения.

```sql
CREATE TABLE products_modern (
    id BIGINT AUTO_INCREMENT PRIMARY KEY,
    title VARCHAR(150) NOT NULL,
    price DECIMAL(10, 2) NOT NULL,
    attributes JSON NOT NULL
) ENGINE=InnoDB;

-- Вставка документа JSON
INSERT INTO products_modern (title, price, attributes) VALUES (
    'Смартфон Ultra X',
    69990.00,
    '{
        "color": "Черный",
        "storage_gb": 256,
        "ram_gb": 12,
        "features": ["5G", "NFC", "Waterproof"]
    }'
);
```

### Извлечение данных из JSON:

* **Оператор `->` (JSON Extract):** Извлекает значение в формате JSON (строки остаются в кавычках `""`).
* **Оператор `->>` (JSON Unquote Extract):** Извлекает "чистое" текстовое значение без лишних кавычек.

```sql
-- Извлечение объема памяти и цвета:
SELECT 
    title,
    attributes->>'$.color' AS color,
    attributes->'$.storage_gb' AS storage
FROM products_modern
WHERE attributes->>'$.color' = 'Черный';
```

### Индексация JSON через виртуальные генерируемые колонки

Хотя сам по себе документ JSON нельзя проиндексировать обычным B-Tree, в MySQL создается виртуальная вычисляемая колонка, по которой строится классический индекс:

```sql
-- Добавляем вычисляемую колонку из поля JSON
ALTER TABLE products_modern 
ADD COLUMN ram_gb INT GENERATED ALWAYS AS (attributes->'$.ram_gb') STORED;

-- Создаем быстрый B-Tree индекс по виртуальной колонке
CREATE INDEX idx_products_ram ON products_modern(ram_gb);
```
